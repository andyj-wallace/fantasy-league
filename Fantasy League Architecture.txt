The worker's job is to run things users don't need to wait for:

Import EPL match data
Calculate player scores
Calculate team scores
Update league standings
Award postponed-match transfers
Monthly price updates


Bad Approach

User opens leaderboard.

```
GET /leaderboard

For each team:
  Calculate player scores
  Calculate captain bonus
  Calculate auto-subs
  Calculate team total
  Calculate rankings

Return response
```

If you have:
       100 leagues
       50 managers per league

you could be recalculating thousands of teams every time someone refreshes.
Very expensive.

Better Approach

Calculate once. Store forever.

Liverpool vs Arsenal finishes.
       Your data provider sends:
       Match Complete
       Liverpool 2 - 1 Arsenal

Importer stores stats: 
       Salah:
              Goal
              Assist

       Saka:
              Goal

Worker sees:

       MATCH_COMPLETED

and runs: calculatePlayerScores(matchId)

Results:

       player_scores

       Salah = 9
       Saka = 6

saved to database.

Then another worker runs: calculateTeamScores(gameweek)

Example:

       Drew FC

       Salah = 9
       Captain Bonus = +9

       Saka = 6

       Team Total = 54

Store:

       team_scores

       team_id=123
       gameweek=8
       score=54

Then: updateStandings()

Store:

       league_standings

       1. Drew FC     502
       2. Bob FC      498
       3. Sarah FC    487

Now when a user opens the leaderboard: `GET /leaderboard`

The API simply does:

       ```
       SELECT *
       FROM league_standings
       WHERE league_id = ?
       ```

and returns it.

No calculations.


What triggers the worker?

Usually events.

       MATCH_COMPLETED
       GAMEWEEK_COMPLETED
       PRICE_UPDATE_DAY
       MATCH_POSTPONED

Football API
   ↓
Cron Job
   ↓
Importer
   ↓
Worker Functions
   ↓
Database


Every 1–5 minutes:
       Poll football provider.
       Find changed matches.
       Recalculate affected scores.
       Update standings.
Simple and scalable enough for thousands of users.

What actually takes the longest?
       Not the frontend.
       Not the APIs.
       The scoring engine.

For example:
       Player starts match
       Gets injured after 8 minutes
       Receives yellow card
       Captain doesn't play
       Vice-captain does play
       Bench substitution occurs
       Match is later ruled postponed

Those edge cases consume a disproportionate amount of development time.
