AWS Deployment Roadmap

A visual, step-by-step guide to deploying Fantasy League to AWS — what each step does, why it is necessary, and why this particular shape is both a best practice and the cheapest sensible way to run the app. A second roadmap at the bottom shows how to migrate to a more scalable infrastructure when growth demands it.

1 · The target architecture (what you are building)

Everything below is created by one CDK stack from a single command. The design has two halves: a public edge (CloudFront serving the static site and proxying the API) and a private VPC where every Lambda and the database live with no path in from the internet. The only bridge between the private world and the outside is a tiny NAT instance for outbound calls (football API, Cognito key fetch, SSM).

2 · Why this shape — best practice and lowest cost at the same time

Every choice below was made by asking two questions: “is this the secure, reproducible way?” and “is there a cheaper option that doesn't compromise the first answer?”. The result is that the security-critical decisions (private DB, no long-lived keys, encrypted everything) cost nothing extra, and the savings come from picking the right tier of each service for MVP scale.

🔒

Security is structural, not bolted on

The database has no public endpoint at all — not a firewall rule, no route. User PII sits behind two layers (private subnet + security group), and passwords never touch it because Cognito owns auth. A leaked connection string alone cannot reach the DB from the internet.

📜

Everything is code (no ClickOps)

One CDK stack defines every resource. cdk deploy is idempotent — rerunning it can never duplicate resources — and cdk diff shows exactly what will change before it does. A fresh AWS account can rebuild the whole environment from one command.

💸

Pay for requests, not for idle

Lambda, HTTP API, EventBridge, S3, CloudFront, Cognito, and SSM all bill per use and round to $0 at MVP traffic. The only always-on costs are the database and a $3/month NAT instance. Nothing is pre-provisioned for load that doesn't exist yet.

3 · Step-by-step deployment flow

Follow the steps top to bottom. Steps 0–2 are one-time setup; steps 3–6 are the actual deployment (and later become the automated pipeline in step 7); step 8 proves it all works. Each card says what the step does, why it must exist, and the best-practice / cost reasoning behind it.

0

Prerequisites

once ever

An AWS account, the AWS CLI configured with admin credentials for the initial setup, and Node.js. All work targets us-east-1 (where the live Cognito pool already exists).

Why necessary Everything after this step is executed as code against this account — there is no console clicking anywhere in the flow.
Best practice Admin credentials are used only for this bootstrap. Day-to-day deploys will use a scoped, short-lived OIDC role (step 7) — humans and CI never hold long-lived keys.
1

Bootstrap CDK in the account

once per account/region
npx cdk bootstrap aws://<account-id>/us-east-1

Creates the small set of support resources CDK needs (an S3 staging bucket and IAM roles for CloudFormation) so it can upload Lambda bundles and execute deployments.

Why necessary CDK compiles your TypeScript into CloudFormation templates + asset bundles. Without the bootstrap bucket/roles there is nowhere to stage those assets — every later cdk deploy depends on this.
Best practice / cost CDK was chosen over raw CloudFormation/Terraform because it's the same language as the repo and NodejsFunction auto-bundles Lambdas with esbuild — no separate build tooling to maintain. Bootstrap resources themselves cost ~$0.
2

Put secrets into SSM Parameter Store

once per environment
aws ssm put-parameter --type SecureString \ --name /fantasy-league/prod/auth-token-secret --value '…' # repeat for: football-data-api-key, cognito-user-pool-id, # cognito-app-client-id (database-url is composed by the stack)

Real secret values are written out-of-band, before the stack exists. The CDK stack only reads them and grants each Lambda access to exactly the parameters it needs.

Why necessary Secrets must never live in the repo, in .env files on a server, or as plaintext in the CloudFormation template. Creating them outside the stack also means a redeploy can never accidentally overwrite or rotate them.
Best practice / cost SecureString parameters are KMS-encrypted at rest, access is IAM-audited, and they cost $0 — Secrets Manager's $0.40/secret/mo only buys managed rotation, which can be added later if wanted.
3

Deploy the stack — cdk diff then cdk deploy

every deploy
npx cdk diff # review: added / changed / REPLACED / destroyed npx cdk deploy # VPC → NAT → RDS → Lambdas → HTTP API → CloudFront

One command builds the entire diagram from section 1: the dedicated VPC with public/private subnets, the fck-nat instance, the private RDS instance, all four Lambdas, the HTTP API, and the CloudFront + S3 frontend shell. Resources follow the fantasy-league-<env>-* naming convention and are tagged for cost allocation.

Why necessary This is the whole infrastructure. Ordering inside the stack matters — the VPC must exist before anything placed in it — and CDK resolves that dependency graph for you. cdk diff first is the review gate that catches an accidental resource replacement (e.g. from renaming a construct) before it destroys something stateful.
Best practice / cost Declarative + idempotent: rerunning deploy with no changes is a no-op and can never create duplicates. Prod gets termination protection and the DB a RETAIN policy, so even deleting the stack cannot silently drop the database.
4

Invoke the migration Lambda — create the schema

every deploy with schema changes
aws lambda invoke --function-name fantasy-league-prod-migrate out.json # fails the pipeline on a non-zero migration result

A dedicated Lambda inside the VPC runs Drizzle's migrator against RDS, creating/updating all tables. It is never scheduled — only invoked deliberately, by CI or by hand.

Why necessary The database is private, so CI cannot reach it to run npm run db:migrate directly — and that's the point. The migration Lambda is the only sanctioned write-path for schema changes, running inside the network boundary.
Best practice / cost This preserves the "no public DB path" guarantee instead of punching a hole in it for CI (the common shortcut that undermines the whole design). Cost: fractions of a cent per invocation.
5

Load player data

once per environment

Run the roster hydration path (hydrate:roster) or the existing seed to populate the ~<1,000 real-footballer Player records. Subject to the API-Football plan tier — tracked separately in remaining-gaps-todo.md.

Why necessary The squad builder and scoring engine are useless without the player universe. This is app data, not infrastructure — which is exactly why it's a separate step from cdk deploy and from schema migration.
Best practice / cost Keeping data loading out of the infrastructure stack means redeploys never re-import or clobber data, and the same stack can be stood up empty for staging.
6

Publish the frontend

every deploy
NEXT_PUBLIC_COGNITO_…=… npx next build # static export → ./out aws s3 sync ./out s3://fantasy-league-prod-web-<account-id> --delete aws cloudfront create-invalidation --paths "/*"

Build the static export with the public build-time env (Cognito IDs; API base is same-origin /api), sync it to the private bucket, and invalidate CloudFront so users get the new version immediately.

Why necessary The bucket is empty until this runs. --delete removes stale pages from previous builds; the invalidation flushes CloudFront's edge caches, otherwise users could see the old site for hours.
Best practice / cost Same-origin /api/* routing through CloudFront eliminates CORS entirely — a whole class of production bugs gone by architecture. S3 + CloudFront serve this for pennies; the first 1,000 invalidation paths/month are free.
7

Automate it — GitHub Actions CI/CD

once, then runs itself

CI on every PR: npm ci → typecheck → vitest, blocking merge. Deploy on push to main (with manual approval): steps 3 → 4 → 6 in order, authenticated via GitHub OIDC assuming fantasy-league-prod-deploy-role. A failed migration fails the whole deploy.

Why necessary Manual deploys drift and get skipped steps. Codifying 3→4→6 makes every deploy identical and reviewable — and this also closes the repo's standing "no CI" gap by putting typecheck + tests in front of every merge.
Best practice / cost OIDC means zero long-lived AWS keys stored in GitHub — credentials are minted per-run and expire in minutes. GitHub Actions is free at this repo's volume.
✓

Verify — the smoke test gate

every deploy
  • curl https://<dist>.cloudfront.net/api/gameweeks/current → 200, no CORS error (proves API-through-CloudFront routing).
  • Hard-refresh /login → page loads, not a 404 (proves the CloudFront Function rewrite).
  • Full click-through: Cognito sign-up → login → create league → squad builder → transfers.
  • Confirm RDS has no public endpoint and refuses connections from anywhere but the Lambda SG.
  • Manually invoke the worker Lambda → a poll cycle logs and writes to RDS.
  • Kill the NAT instance → ASG relaunches it in ~2–4 min; a missed worker poll simply retries next cycle.
Why necessary Each check maps 1:1 to a deliberate design decision — if one fails, you know exactly which decision didn't land. Deploy to a throwaway/staging stack first; environments are isolated stacks, so staging can never touch prod.
Best practice Testing the failure mode (killing the NAT) on purpose, before launch, is what makes the $3/mo NAT instance a safe trade instead of a gamble.

5 · Roadmap: migrating to more scalable infrastructure

The MVP architecture was deliberately chosen so that scaling up is a series of component swaps, not a rewrite — the app code (route table, workers, Drizzle/Postgres) is untouched at every stage. And because the read path is precomputed ("calculate once, store forever"), leaderboard reads scale almost for free; the pressure points that actually appear are database connections, worker throughput, and availability guarantees — which is exactly what these stages address, in order.

Rule: migrate on evidence, not anticipation. Each stage has an explicit trigger — until you observe it, staying at the current stage is the best practice, because unused capacity is pure cost.

0

Today — MVP serverless (you are here)

~$0–18 / mo

Single-AZ RDS micro, NAT instance, on-demand Lambdas, default CloudFront domain. Comfortably serves the design target: <1,000 players, a handful of leagues, low concurrency. Everything above this line in the document.

1

Stage 1 — Production hardening

adds ~$35–55 / mo
Migrate when Real users depend on the app (public beta / first paying league), so a 2–4 minute background-job blip or a single-AZ outage is no longer an acceptable trade for a few dollars.
  • fck-nat → managed NAT Gateway — a one-line CDK change (NatProvider.gateway()). Zero-maintenance, multi-AZ-capable egress. (+~$32/mo)
  • RDS single-AZ → Multi-AZ — synchronous standby in the second AZ with automatic failover; the subnet group already spans 2 AZs, so this is a flag flip. (~2× DB cost, +~$14/mo)
  • Custom domain — Route 53 hosted zone + free ACM certificate on CloudFront. (+$0.50/mo + domain)
  • Alarms & visibility — CloudWatch alarms on Lambda errors, RDS CPU/storage/connections, worker failures; keep the Budgets alarm. (~$0–2/mo)
  • Optional: WAF on CloudFront — managed rules against common abuse, revisiting the documented MVP scope-cut. (+~$6–10/mo)

Nothing about the application changes — these are availability and trust upgrades to the exact same topology.

2

Stage 2 — Relieve the first real bottlenecks

adds ~$15–40 / mo
Migrate when Metrics — not intuition — show pressure: RDS connection count nearing its limit as Lambda concurrency grows, sustained RDS CPU during match windows, or cold-start latency showing up in API p95 during traffic spikes.
  • Add RDS Proxy between Lambdas and Postgres — pools and multiplexes connections so hundreds of concurrent Lambdas can't exhaust the DB. This is the canonical Lambda-meets-RDS scaling fix; the app keeps using DATABASE_URL, only the host changes. (+~$11–15/mo)
  • Instance right-sizing — db.t4g.micro → small/medium based on observed CPU/memory; a restart-sized change, not a migration.
  • Provisioned concurrency (API Lambda only) — keeps 1–2 warm instances during match windows to remove cold starts; can be scheduled to match-day hours only to cap cost. (+~$4–10/mo)
  • Raise reserved concurrency limits deliberately, now that the proxy protects the connection pool.
  • Optional: read replica — only if non-precomputed reads (squad browsing, player search) measurably load the writer. The precompute pattern makes this later than in most apps.
3

Stage 3 — Scale-out architecture

~$150–400+ / mo
Migrate when Growth is structural, not spiky: thousands of active leagues, sustained (not bursty) API traffic where always-on compute is cheaper than per-request Lambda, or worker cycles pushing the 15-minute Lambda ceiling as the fixture/league count multiplies.
  • RDS → Aurora PostgreSQL (Serverless v2 for spiky match-day load, provisioned for steady load) — wire-compatible with Postgres, so Drizzle and the schema move unchanged; brings storage autoscaling, fast failover, and up to 15 low-lag read replicas.
  • Scoring pipeline → queue-decoupled workers — EventBridge events push MATCH_COMPLETED / GAMEWEEK_COMPLETED onto SQS; scoring consumers scale horizontally with per-message retries and a dead-letter queue. The importer → playerScores → teamScores → standings stages already have clean boundaries, so this is a transport change, not a redesign.
  • API on ECS Fargate behind an ALB — only if sustained request volume makes always-on containers cheaper than Lambda, or per-request latency budgets tighten. The handler-per-route structure ports directly (the local server in src/api/localServer.ts already proves the non-Lambda hosting path).
  • ElastiCache (Redis) in front of hot reads (current gameweek, fixtures) if needed — though precomputed tables keep read cost low for a long time.
  • Multi-region — last resort, driven only by a global audience with latency SLAs; CloudFront already handles global static delivery, so this applies to the API/DB tier alone.
Why the stages are ordered this way: each stage buys the next constraint you'll actually hit — availability first (stage 1), then database connections and latency (stage 2), then raw throughput (stage 3). Skipping ahead buys capacity you can't use yet at a price you notice immediately. The inverse also holds: every stage is reversible, because all of it is CDK — rolling back an upgrade is a cdk diff + cdk deploy away.
