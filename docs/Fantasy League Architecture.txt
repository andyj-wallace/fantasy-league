VAR and Late-Arriving Corrections

"Calculate once, store forever" applies to player_scores / team_scores / league_standings — not to the raw imported stats feeding them. While a match is in progress, PlayerMatchStat rows are upserted on every poll and are expected to change; that's provisional staging data, not a violation of the rule.

VAR reversals (goal cancelled, penalty confirmed/overturned) are reconciled by the importer, before anything is written to PlayerMatchStat — net a cancelled goal against the goal it overturns so the scoring engine never has to know VAR exists. In practice this is mostly free: VAR reviews resolve during the match, so the provider's event list is normally already final by the time a fixture reaches FT.

The residual risk is the rare post-match correction (provider fixes a stat, or a disciplinary panel overturns a card, after MATCH_COMPLETED already fired). Handle this with one bounded confirmation re-poll — e.g. 30–60 minutes after MATCH_COMPLETED — that re-pulls stats once, re-runs the calculators only if something actually changed, then freezes for good. Still event-driven and bounded; not per-request recalculation.

Match.status (the provider's raw status string) is the only "is this match still moving" state the importer needs — it decides whether a fixture is worth a per-fixture call at all, and isn't a separate state machine.


What triggers the worker?

Usually events.

       MATCH_COMPLETED
       GAMEWEEK_COMPLETED
       PRICE_UPDATE_DAY
       MATCH_POSTPONED

Match Status → Worker Trigger Mapping

Provider fixture statuses map onto the two completion-related triggers above:

       FT, AET, PEN          → MATCH_COMPLETED  (regular time, extra time, and penalty-shootout finishes all count as complete)
       PST                   → MATCH_POSTPONED  (drives the postponed-match free-transfer rule)

Open question, not yet decided: ABD (abandoned), CANC (cancelled), WO (walkover), AWD (technical loss) aren't covered by either trigger today. None of these are "postponed" (rescheduled) or a normal completed match, so neither existing rule cleanly applies — needs a product decision before the importer can handle them.

Continuously, at a cadence the Live-Match Polling Strategy below computes from the daily request budget:
       Poll football provider.
       Find changed matches.
       Recalculate affected scores.
       Update standings.
Simple and scalable enough for thousands of users.

Live-Match Polling Strategy

The provider caps us at 100 requests/day. Checking our own remaining quota (the provider's account/status endpoint) doesn't count against that cap, so it's free to call as often as we want — that's the throttle signal the strategy runs on, instead of a fixed conservative number baked in ahead of time.

Per-fixture detail calls (events + players) cost 2 requests per check, per fixture, regardless of how many other fixtures are live at the same time — there's no batching across fixtures for that data. The broad fixtures list (one call covers every currently-live fixture's status) is the only call that scales for free across however many matches are live.

       1. Discovery (≈1 call/gameweek): pull the gameweek's fixture list once for kickoff times — these rarely change outside a postponement.
       2. While any match is live, each cycle:
              a. Call the (free) quota-status endpoint for requests remaining today.
              b. Call the broad live-fixtures list (1 call) to see which fixtures are still in play.
              c. For each fixture still live, pull events + players (2 calls/fixture).
              d. Compute the next cycle's wait time from what's actually left: remaining quota ÷ (live fixtures today × 2 calls), spread over the remaining live minutes today — recalculated every cycle, not fixed in advance.
       3. Fixture status flips to a terminal state (FT/AET/PEN) → final events/players pull, fire MATCH_COMPLETED, stop polling that fixture.
       4. ~45–60 min after MATCH_COMPLETED: one confirmation re-poll for VAR/late corrections — on by default now that budget supports it; the first thing to skip if a day runs unusually hot.

Worked example, busiest single day in a gameweek (~7 concurrent Premier League fixtures, the Saturday 3pm cluster): reserving ~5 calls for discovery/injuries/admin leaves ~95 for live tracking. Each fixture's live window is ~105–120 min; ~6–7 check rounds per fixture (2 calls each) is ~13–14 calls/fixture × 7 ≈ 95 — landing on a check roughly every 15–18 minutes per fixture. Quieter days (1–2 fixtures) get a tighter cadence automatically, since the same formula divides a near-untouched budget across fewer matches.

The quota-status check is what makes this safe to run hot: if a day runs long (extra time, delayed kickoffs, more concurrent fixtures than usual), step 2d sees the shrinking quota in real time and widens the interval on its own — no hardcoded conservative ceiling required.

Player Availability Status

The provider doesn't give a clean injury-vs-suspended split: its `type` field only has two values (Missing Fixture, Questionable). "Suspended" shows up only buried in the free-text `reason` field, not as its own type. Robust simple model:

enum PlayerAvailabilityStatus {
  AVAILABLE       // no entry for this player/fixture
  OUT             // type: "Missing Fixture"
  QUESTIONABLE    // type: "Questionable"
}

Keep the raw `reason` string ("Knee Injury", "Suspended", "Illness", etc.) as a separate plain-text field alongside the enum, for tooltip/label display — don't string-match it into a 4th `SUSPENDED` value, since that's fragile across providers/leagues.
