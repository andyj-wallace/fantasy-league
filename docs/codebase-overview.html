New-Dev Walkthrough

A plain-language tour of what actually happens when you run this app, written for someone opening the repo for the first time.

Five folders matter, and they all agree on one shared vocabulary:

  • src/domain — plain TypeScript interfaces (League, Team, Player, …). No logic, just the shape of every concept in the product. Every other layer imports from here.
  • src/db — the Postgres schema, written with Drizzle ORM, plus a generated SQL migration. Mirrors the domain types table-for-table.
  • src/api — one file per HTTP endpoint, shaped like an AWS Lambda handler so the exact same function can run locally or deployed.
  • src/workers — background jobs, meant to run on a schedule (EventBridge in prod), not in response to a request.
  • src/app — the Next.js frontend, one folder per route.

Walking through "Create a League" end to end

  1. You load /leagues/create (src/app/leagues/create/page.tsx) — a client component with a plain HTML form.
  2. On submit, it does a raw fetch() straight to {API_BASE_URL}/leagues with a JSON body. There's no shared API client — every page writes its own fetch call.
  3. In dev, that request lands on localServer.ts — a small hand-rolled Node http server that regex-matches the method+path against the table in routes.ts.
  4. The matched handler, createLeague.ts, runs: it JSON.parses the body and passes the fields into createMockLeague() from mocks.ts, which returns a hardcoded League object with your overrides spliced on top. No database is touched.
  5. The handler wraps that object in jsonResponse() and the local server writes it back as the HTTP response body.
  6. In production, the identical handler function would be deployed as a Lambda behind API Gateway — that's the entire reason ApiHandlerEvent only picks the few fields of APIGatewayProxyEvent the handlers actually read: same code, two entrypoints (api/index.ts locally vs. the Lambda runtime invoking the handler directly).

The worker side, briefly

Same two-entrypoint idea: handler.ts for Lambda/EventBridge, localScheduler.ts for a local setInterval loop. Both just call runWorkerCycle(), which is meant to be the full "poll provider → import → score → standings" pass but today only performs step one — and that step (importMatchData) is itself an empty function body.

Bottom line

Reading any handler or worker function today tells you what its eventual behavior will be — names are deliberately self-documenting, per CLAUDE.md. But actually running the app right now only exercises the mock-data path end-to-end: nothing you do in the UI persists anywhere.

Gaps & Risks

Most of these are expected at the current build stage, not bugs — flagged here so they're tracked as explicit next steps rather than discovered by surprise.

#SeverityAreaGapWhy it matters
1HighDatabase Zero call sites for db/client.ts Every handler reads/writes only in-memory mocks; nothing persists between requests yet. Expected at this build stage — next concrete milestone per the build order.
2HighWorkers Scoring pipeline 80% orphaned — calculatePlayerScores, calculateTeamScores, updateStandings, awardPostponedMatchTransfers, runMonthlyPriceUpdate are never invoked anywhere Per ROADMAP.txt this scoring engine is where most of the project's effort goes — it's worth confirming the wiring plan before fleshing out the bodies.
3HighSecurity No authentication anywhere — userId / commissionerUserId are plain client-supplied strings, login page is static Once real persistence lands, any caller can act as any user (e.g. removeManager would let anyone remove anyone). Needs an auth layer before real data is exposed.
4MediumAPI / Domain Team.rosterSlots (embedded array) vs. team_roster_slots (normalized table) — no mapping/repository layer exists between the two shapes This translation is undesigned, not just unimplemented — worth deciding the repository pattern before wiring the DB into handlers.
5MediumAPI No runtime input validation — handlers do JSON.parse(event.body ?? "{}") as SomeType with no schema check Missing/malformed fields pass through silently as undefined; non-JSON bodies throw inside JSON.parse uncaught.
6MediumAPI No try/catch around matched.route.handler(event) in localServer.ts:64 Any thrown error (e.g. bad JSON body) crashes that request instead of returning a 4xx, with no centralized error response shape.
7LowQuality No test files (*.test.ts) and no CI workflow (.github/workflows) anywhere in the repo npm run typecheck is currently the only automated check — fine pre-MVP, worth adding before real logic lands in the worker stubs.
8LowWorkers localScheduler.ts uses an in-process setInterval Fine for one dev machine; would double-process if ever run as more than one instance against a real DB. Production already avoids this via a single EventBridge rule, so this is a dev-only footnote.
9LowDatabase db/client.ts builds a pg.Pool at module load with no connection error handling First import will hang or throw if DATABASE_URL is unset or Postgres is unreachable — no retry/backoff or startup health check.

Scaling Considerations

V1 explicitly targets a small scale (fewer than 1,000 Player records, per CLAUDE.md) — these are forward-looking notes, not blockers for V1.

TopicCurrent designNote
Leaderboard reads getLeagueStandings is designed to be a flat SELECT against the precomputed league_standings table once wired Good — matches the "calculate once, store forever" mandate in the architecture doc; the anti-pattern it explicitly warns against (recomputing every team's score on read) isn't present.
jsonb columns player_scores.breakdown and league_standings.tiebreaker_stats stored as jsonb Trades query-ability for flexibility — fine at this scale, but neither column can be filtered/sorted in SQL without JSON operators if a future feature needs e.g. "sort by goal points."
Pagination None on searchPlayers or getLeagueStandings Acceptable under the stated <1,000-player / small-league target; revisit if that assumption changes.
Schema/migration drift schema.ts is hand-edited, db:generate produces the migration manually Nothing enforces the migration stays in sync with schema.ts — no CI check comparing the two. Low risk solo, worth a pre-commit or CI check once more than one person touches the schema.
